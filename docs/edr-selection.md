# Критерии выбора EDR (этап 3 программы защиты от вредоносного кода)

Документ для запроса коммерческих предложений и внутренней оценки. Относится к карточке **PB-46** в проблембуке: сначала управляемость антивируса и миграция контроллера домена, затем EDR на поддерживаемых ОС.

## Зачем и почему не сейчас

Антивирус ловит известное (сигнатуры), EDR — поведение: запуск PowerShell из офисного документа, чтение памяти LSASS, создание службы из временного каталога, боковое перемещение. Для домена это важнее сигнатур.

Но на **Windows Server 2012 R2** современный EDR работает урезанно, потому что в самой ОС нет нужных механизмов:

| Механизм | Появился в | На 2012 R2 |
|---|---|---|
| AMSI (проверка скриптов в памяти) | Windows 10 / Server 2016 | нет |
| Правила ASR в Defender | Server 2019 | нет |
| Credential Guard (VBS) | Server 2016 | нет |
| ETW-TI (телеметрия угроз) | Windows 10 1809+ | нет |
| Поддержка ОС вендором | — | завершена 10.10.2023 |

Поэтому EDR ставится **после** перевода контроллера домена на поддерживаемую ОС. До этого разрыв закрывается компенсирующими мерами: KES с исключениями под управлением KSC, Sysmon, Windows Event Forwarding, аудит AD.

## Стоп-условия (при любом из них предложение отклоняется)

1. Вендор заявляет поддержку Server 2012 R2, но с ограничениями по ключевым функциям — как решение для DC не рассматривается, только как временная мера.
2. Нет централизованной консоли (облачной или локальной) и централизованных обновлений компонентов и баз.
3. Нет возможности задать исключения по путям, процессам и файлам — обязательное условие для AD, SYSVOL, баз 1С и лицензий HASP.
4. Не определено, **кто разбирает срабатывания**. Без этого EDR — дорогой сбор логов: детект без реакции не защищает.
5. Требуется постоянный доступ агента во внешний интернет без прокси или собственного релея в закрытом сегменте.

## Обязательные требования

| № | Требование | Как проверять |
|---|---|---|
| 1 | Поддержка целевых ОС: Windows Server 2022/2025, Windows 10/11; наличие дорожной карты по 2025+ | матрица поддержки вендора, дата окончания поддержки текущей версии |
| 2 | Централизованная консоль: управление политиками, инвентаризация, статус агентов и баз | демо или тестовая установка |
| 3 | Централизованное обновление: компоненты, базы, контент; управляемый источник; работа в закрытом сегменте | политика обновлений, поддержка внутреннего репозитория и офлайн-обновления |
| 4 | Исключения: пути, процессы, хеши, расширения; отдельный профиль для контроллера домена | список исключений, рекомендованных вендором для AD |
| 5 | Поведенческая аналитика: подозрительные цепочки процессов, LSASS access, persistence, lateral movement | список покрываемых техник (ATT&CK), демо детектов |
| 6 | Реакция: изоляция хоста, карантин, удаление артефактов, откат изменений (если заявлен) | демо, ограничения по ОС |
| 7 | Роли и аудит: разграничение администраторов, журнал действий, экспорт для аудита | матрица ролей, отчёты |
| 8 | Интеграция: API и выгрузка событий в SIEM/лог-сервер (CEF, syslog, webhook) | документация API, тестовая выгрузка |
| 9 | Ресурсы: требования к CPU/RAM/диску на сервере и на контроллере домена | замер на пилоте, не «по паспорту» |
| 10 | Совместимость: AD DS, DNS, 1С (файловая и клиент-серверная), HASP/Sentinel, RDS, SQL Server | пилот на копии, проверка входа, 1С и печати |
| 11 | Обновления и поддержка: SLA на реакцию техподдержки, сроки выпуска баз под новые угрозы | договор, регламент поддержки |
| 12 | Документация и интерфейс на русском языке; наличие в реестре отечественного ПО, если требуется | подтверждение вендора |

## Желательные требования

- Управляемое обнаружение и реагирование (MDR) как опция — критично, если своего аналитика нет.
- Покрытие терминальных серверов (RDS) и серверов без выхода в интернет.
- Обогащение детектов (репутация, sandbox, threat intelligence).
- Отчёты для аудита ИБ и страхования: покрытие, свежесть баз, история инцидентов.
- Мобильное оповещение и интеграция с мессенджером для дежурства.
- Возможность пилота 30 дней без обязательств.

## Если EDR не выбран

Промежуточный уровень, который закрывает основную часть риска без смены продуктов:

1. **KES под управлением KSC** — единая политика, управляемый источник обновлений, отчёты о покрытии и свежести баз.
2. **Sysmon** с минимальным профилем (процессы, сетевые соединения, загрузка драйверов, доступ к LSASS) на серверах.
3. **Windows Event Forwarding** на выделенный сервер или в лог-центр с хранением не менее 90 дней.
4. **Аудит AD**: вход, изменение учётных записей, доступ к каталогу, изменение политик.
5. **Регламент**: кто смотрит события, с какой периодичностью, что считается инцидентом и как он эскалируется.

Такой набор работает на Windows Server 2012 R2 и не требует миграции, чтобы начать действовать. Он же становится доказательной базой при аудите ИБ и страховании.
